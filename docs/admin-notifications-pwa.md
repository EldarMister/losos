# Уведомления и приложение NAKTA

## Как пользоваться

В верхней части любого разрешённого раздела есть «Уведомления и приложение». Сотрудник отдельно включает звук, выбирает громкость и проверяет сигнал. Браузер разрешает аудио только после действия человека; после перезапуска вкладки может понадобиться повторное включение. Громкость и предпочтение сохраняются для конкретного сотрудника в этом браузере. Звук требует Web Locks: при отсутствии безопасной синхронизации вкладок остаются визуальные уведомления.

Системные уведомления включаются отдельной кнопкой. Разрешение браузера запрашивается только после её нажатия. На iPhone/iPad нужно установить приложение через Safari → «Поделиться» → «На экран Домой», открыть установленное приложение и включить уведомления там. В остальных браузерах используется доступная команда установки; если её нет, панель продолжает работать на сайте.

Новый заказ показывает свой бизнес-номер и кнопку перехода. Состав, адрес, телефон и имя клиента в push не передаются. Переход открывает обычную страницу, заново проходящую проверку сессии и права просмотра. Фоновая доставка зависит от браузера, ОС, энергосбережения и разрешения; она не гарантируется. Звук вкладки и Web Push — отдельные механизмы.

Если панель уже открыта, системное уведомление передаёт переход самой панели: несохранённая форма требует подтверждения, отмена сохраняет её содержимое. При отсутствии открытой панели уведомление открывает новую вкладку.

## Конфигурация сервера

Для production необходим HTTPS на сайте и API. `NEXT_PUBLIC_API_URL` должен указывать на API соответствующего окружения с суффиксом `/api`; `FRONTEND_ORIGIN` — содержать разрешённый origin панели. Нельзя направлять тестовую сборку на production API.

Один раз создайте VAPID-ключи в защищённом окружении администратора:

```powershell
cd server
npx web-push generate-vapid-keys --json
```

Сохраните на сервере:

```text
ADMIN_VAPID_PUBLIC_KEY=<publicKey>
ADMIN_VAPID_PRIVATE_KEY=<privateKey>
ADMIN_VAPID_SUBJECT=mailto:<рабочий адрес поддержки>
```

Приватный ключ нельзя добавлять в Git, `NEXT_PUBLIC_*`, браузерную сборку или журнал. Публичный ключ выдаётся авторизованному сотруднику по `GET /api/admin/push/config`. Пока значения не настроены, SSE и звук работают; UI честно сообщает, что системные уведомления не настроены. При смене VAPID-ключей пользователи должны отключить и снова включить системные уведомления.

API должен работать как долгоживущий процесс: в нём поддерживается SSE и раз в 3 секунды обрабатывается очередь Web Push. Для reverse proxy отключите буферизацию `/api/admin/events`, разрешите длительные ответы и передавайте `Authorization`. Сервер дополнительно возвращает `X-Accel-Buffering: no` и `Cache-Control: no-store`. Обычный serverless runtime со спящим процессом не обеспечивает своевременный фоновой диспетчер; для него нужно отдельно запускать этот API как worker/service.

Разрешены только HTTPS endpoints известных push-провайдеров Google, Mozilla, Apple и Windows. Новые провайдеры требуют явного изменения allowlist в `admin-notification-policy.ts`. Это ограничивает SSRF через произвольный URL подписки.

## Данные, права и повторное подключение

Миграция `1785011000000-AddAdminNotifications` добавляет две таблицы, не изменяя исторические заказы. `admin_order_events` записывается в той же транзакции, что новый заказ. Событие становится доступно потребителям только после commit. Повтор оформления по существующему idempotency key не создаёт второй event; уникальный `orderId` дополнительно защищает очередь.

Короткая финальная запись события защищена транзакционной advisory-блокировкой: номера событий следуют порядку commit, поэтому параллельный быстрый заказ не заставит SSE пропустить ещё не завершённый заказ с меньшим номером.

SSE проходит авторизацию при подключении, затем каждые 2 секунды и перед каждой выдачей события. Без `orders.view`, при блокировке, истечении или удалении сессии поток прекращается. Клиент обновляет авторизацию. Первое подключение начинается с текущего курсора без звуков для старых заказов. После разрыва сохранённый курсор позволяет восстановить события, а сигнал синхронизации обновляет актуальный список и счётчики. События старше 30 секунд не звучат; старше двух минут не создают всплывающее уведомление. Короткие разрывы не теряют новые заказы.

После восстановления БД или смены API сохранённый курсор браузера может превышать текущую последовательность. При подключении сервер сбрасывает такой курсор на текущий и отправляет sync; будущие заказы снова приходят сразу.

Heartbeat несёт тот же курсор, а браузер сохраняет cursor только из sync/order.created. Автоматические транспортные ID SSE не используются как последовательность заказов.

На одном устройстве все вкладки сотрудника используют атомарную Web Lock и общий журнал UUID событий. Только одна вкладка получает право воспроизвести сигнал. В журнале нет данных клиента. Системные уведомления имеют отдельный атомарный журнал service worker и стабильный `tag`.

Push-подписка принадлежит конкретной серверной сессии. Один endpoint привязывается только к одному текущему сотруднику. Перед каждой отправкой повторно читаются активность сотрудника, текущие права и действительность сессии. Выход/смена пароля/блокировка удаляет серверную сессию, а FK `ON DELETE CASCADE` удаляет подписку. Клиент дополнительно снимает подписку браузера и закрывает уведомления. Недоступные endpoints (404/410) удаляются. Диспетчеры нескольких экземпляров API используют `FOR UPDATE SKIP LOCKED`, поэтому событие обрабатывается одним экземпляром; повтор после аварии подавляется service worker. События старше двух минут после простоя не рассылаются. Временная ошибка отдельного push не откатывает заказ; заказ всё равно доступен через SSE/список.

## Кэш, offline и обновления

Manifest и service worker ограничены `/admin`; клиентский магазин не входит в область. Для `/admin/sw.js` задан заголовок `Service-Worker-Allowed: /admin`, поскольку основной маршрут проекта — `/admin` без завершающего слеша. `Cache-Control: no-cache` позволяет обнаруживать обновления worker.

Кэшируются только явно перечисленные публичные иконки, manifest, нейтральная offline-страница и распознанные по хэшу неизменяемые JS/CSS из `/_next/static/`. Development chunks со стабильными именами исключены, чтобы обновления кода и стилей не застревали в service worker. Авторизованные API, HTML панели, клиенты, заказы и отчёты не кэшируются. При отсутствии сети виден статус «Нет соединения»; при холодном запуске показывается нейтральная offline-страница. Background Sync и скрытой очереди изменений нет. Повторное подключение не отправляет критичные действия автоматически.

Новый worker остаётся в состоянии waiting. Пользователь видит «Доступна новая версия» и сам подтверждает перезагрузку после сохранения форм. Вызова автоматического `skipWaiting()` при установке нет. Перед выпуском нового набора публичных ресурсов увеличьте `VERSION` в worker; старые кэши с префиксом `nakta-admin-static-` очищаются при активации. Кэши других приложений не затрагиваются.

## Проверка и откат

Проверки чистых функций:

```powershell
node --import ./server/node_modules/tsx/dist/loader.mjs --test server/test/admin-notifications.test.ts
```

Проверяются одновременная доставка одного события в 12 вкладок, повтор после reconnect, отдельные сотрудники, старые события, SSE framing и запрет внутренних/произвольных push endpoints. Интеграционный сценарий `server/test/admin-notifications.integration.cjs` допускает только локальную БД с `test` в имени; он проверяет видимость события после commit и отсутствие после rollback, поток при отзыве прав, хранение подписки и удаление после logout.

Для отката интерфейса используйте предыдущую Git-версию приложения. Новые таблицы и будущие события можно оставить: старый код их не читает. Не откатывайте миграции рабочей БД без отдельной проверки зависимостей и резервной копии. Чтобы остановить Web Push, удалите VAPID-конфигурацию из процесса и перезапустите API. Уже доставленные уведомления невозможно гарантированно отозвать средствами сервера.

### Локальная проверка в браузере

`server/test/local-admin-environment.cjs` допускает только явный `TEST_DATABASE_URL` на localhost с `test` в имени БД, отключает внешние интеграции и Web Push. Подготовка через `prepare-admin-browser-test.cjs` создаёт отмеченных «ТЕСТ» сотрудников и три заказа. Состояния preparing/completed задаются как начальные данные теста; это не подтверждение успешной отправки EDU POS. `start-admin-browser-test.cjs` запускает API на 4100 с CORS для локальной панели на 3100/3102.

Откройте панель, войдите тестовым владельцем, включите звук явным нажатием и дождитесь «Заказы обновляются». Затем из корня проекта создайте один новый реальный заказ в тестовой БД:

```powershell
$env:TEST_DATABASE_URL='postgres://losos@localhost:55433/admin_redesign_test'
node server/test/create-admin-realtime-test-order.cjs
```

Помощник создаёт новый заказ при каждом запуске; используйте только для согласованной проверки. Проверьте уведомление с напечатанным бизнес-номером, обновление списка и счётчика, однократный звуковой сигнал. В двух вкладках один event должен запускать один сигнал. Отключение сети должно показывать явное предупреждение; после подключения список синхронизируется. Нажатие системного уведомления при открытой изменённой форме должно запрашивать подтверждение и сохранять форму при отмене. Локальный помощник не проверяет реальную доставку Web Push провайдерами: для неё требуется отдельно настроенное HTTPS-окружение и VAPID.

### Зафиксированные проверки 12 октября 2026

- Unit: 8/8, включая dedup в 12 вкладках, heartbeat cursor, защиту перехода из push и исключение development/API из кэша.
- PostgreSQL integration: commit/rollback/idempotency, конкурентный порядок событий, восстановление устаревшего cursor, отзыв прав SSE, минимальный push payload и удаление подписки после logout — успешно.
- Реальный HTTP `/api/admin/events?after=99999`: sync и heartbeat вернули одинаковый текущий cursor20; чужой транспортный ID больше не увеличивает курсор.
- В браузере новый локальный заказ №27 показал уведомление на открытом разделе аналитики; кнопка открыла его настоящую карточку, cursor изменился с20 на27.
- Две чистые вкладки одного сотрудника получили уведомление о заказе №28. Инструментализация WebAudio до загрузки страницы показала счётчики запуска oscillator 1+1 до события и 1+2 после него: ровно один новый звуковой сигнал на две вкладки. Фильтрация и обновление данных не изменили счётчики; cursor остался28. Это проверка вызова WebAudio, а не прослушивание физических динамиков.
- Обновление service worker v1→v2: отмена подтверждения не перезагрузила панель; после согласия активировался v2 и старый cachev1 исчез. Изменённые стили загрузились заново.
