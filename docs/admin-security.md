# Учётные записи сотрудников

Новая админка использует отдельные учётные записи персонала; клиентские телефонные аккаунты не меняются. Роли: `OWNER`, `ADMIN`, `MANAGER`. Пароли хранятся как salted scrypt (N=32768, r=8, p=1). Случайный токен сессии действителен 12 часов, на сервере хранится только SHA-256. Передавайте его в `Authorization: Bearer`; прежний `x-admin-token` больше не даёт доступ к административным API. Ответы авторизованных запросов имеют `Cache-Control: no-store`.

## Первый владелец

На тестовом окружении примените миграции обычным запуском API. Для первого владельца временно задайте серверные `ADMIN_BOOTSTRAP_ENABLED=true` и `ADMIN_TOKEN` (случайный секрет не короче 32 символов). Отправьте `POST /api/admin/auth/bootstrap` с `{bootstrapToken,login,name,password}`. Пароль — от 12 символов. Эта операция доступна только при полном отсутствии сотрудников, защищена блокировкой транзакции и ограничением попыток. Сразу после создания установите `ADMIN_BOOTSTRAP_ENABLED=false`; удалите bootstrap-секрет из клиентских хранилищ. Никогда не размещайте его в `NEXT_PUBLIC_*` или исходниках.

Вход: `POST /api/admin/auth/login {login,password}`. Ответ: `{token,expiresAt,staff}`. `GET /api/admin/auth/me` возвращает актуальные права. `POST /api/admin/auth/logout` удаляет текущую сессию и связанные push-подписки. `PATCH /api/admin/auth/password {currentPassword,password}` меняет собственный пароль и завершает остальные сессии. Сброс пароля другим сотрудником разрешён только владельцу; он завершает все сессии целевого сотрудника.

## Права

Каталог разрешений: `GET /api/admin/permissions`. Персональная матрица: `allow`, `deny`, `inherit`; наследование также задаётся отсутствием ключа. `{permissions:{}}` сбрасывает все исключения. Для действия необходимо право просмотра того же раздела. OWNER всегда имеет все права; его permissions не могут отозвать доступ. ADMIN по умолчанию имеет все рабочие права. MANAGER имеет `orders.view`, `orders.edit`, `orders.status`, `customers.view`, `customers.edit`. Массовых операций в существующем API нет, поэтому фиктивное право на них не вводится. Экспорт отчётов отдельно защищён `analytics.export`, экспорт в POS — `integrations.export`.

Создание учётной записи (назначение начальной роли), изменение роли/permissions и изменение владельца доступны только OWNER. Ограниченный администратор не может создать нового менеджера и таким образом вернуть себе отозванные права. `PATCH /staff/:id` принимает только name/active/password; поле role/permissions на этом пути отклоняется до фильтрации DTO. Отдельный `PATCH /staff/:id/access` доступен только владельцу. Владелец может назначить дополнительного владельца. Отключение/понижение последнего активного владельца запрещено. Все операции управления персоналом сериализуются advisory lock внутри PostgreSQL-транзакции, поэтому две параллельные операции не могут убрать всех владельцев.

Guard проверяет роль, активность, сессию и персональные исключения в БД при каждом запросе; JWT с устаревшими правами не используется. Общие endpoints каталога/городов проверяют разрешения по изменяемым полям. Агрегированные ответы dashboard/settings скрывают недоступные данные. Общий список городов для фильтров содержит только минимальные идентификаторы и названия, если подробный доступ запрещён.

## Журнал и клиентские карточки

`admin_audit` хранит сотрудника, время, действие и цель. Изменения ролей/прав хранят предыдущие и новые значения; пароли, токены, секреты и полные запросы не записываются. Для рабочих CRUD-запросов сохраняются названия изменённых полей после успешного действия. Изменения персонала и их аудит находятся в одной транзакции; общий CRUD-аудит выполняется после операции, а не атомарно с ней. Данные собираются только с момента применения миграции; исторические действия не восстанавливаются искусственно.

Редактируемые имя и заметка клиента хранятся отдельно в `admin_customer_profiles`; телефон остаётся идентификатором, сохранённые имена, суммы и состав старых заказов не меняются.

Миграция `1785010000000-AddAdminSecurity` добавляет только новые таблицы `admin_staff`, `admin_sessions`, `admin_audit`, `admin_login_attempts`, `admin_customer_profiles`. Она не пересоздаёт существующие данные. Откат миграции удалит новые учётные записи и журнал, поэтому для переключения версии приложения используйте резервную копию и согласованный план отката; автоматический rollback БД не запускался.

## Проверки

`npm run test:admin-security` запускает модульные проверки политики доступа, защиты общих API, отсутствия секретов и хеширования паролей. Чтобы включить HTTP/PostgreSQL-проверки, явно задайте `ADMIN_SECURITY_TEST_DATABASE_URL` на локальную тестовую БД, имя которой содержит `test`; например `postgresql://losos@localhost:55433/admin_redesign_test`. Тест создаёт случайную изолированную схему и удаляет только её в завершении. Рабочая схема и production-конфигурация не используются.

12 октября 2026 года выполнены все 16 тестов без ошибок: прямые запрещённые запросы, обход старым токеном, массовое присваивание role/permissions, попытка ADMIN повысить себя или создать обходную учётную запись, изменение прав при открытой сессии, прекращение активного потока уведомлений после отзыва прав, выход с удалением push-подписки, блокировка сотрудника, отсутствие секретов в журнале и параллельное понижение двух последних владельцев. Серверная сборка также выполнена успешно. Это отдельное тестовое приложение с настоящими модулями безопасности и уведомлений и заглушенными бизнес-сервисами для маршрутов; расчёты каталога/заказов проверяются отдельными тестами.
